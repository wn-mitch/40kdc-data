# Contributing

## Schema Changes

Schema changes affect every downstream tool and language port. Before changing a schema:

1. Open an issue using the **Schema Change** template.
2. Describe the proposed change and its motivation.
3. State whether the change is breaking (requires data migration).
4. Wait for maintainer sign-off before opening a PR.

## Enrichment Data

Enrichment data (phase mappings, timing flags, interaction flags, and Ability DSL entries) lives under `data/enrichment/`.

1. Fork the repository and create a branch.
2. Add or update files under `data/enrichment/`.
3. Run `cd tools && npm run validate` to check schemas and referential integrity.
4. Open a PR summarizing what was added or updated.

### Authoring Ability DSL Entries

Ability mechanics are authored through the semantic-authoring workbench (`tools/src/semantic-authoring/`).

In brief: models propose segmentation, semantic families, and parameters; a human reviewer authorizes trusted leaves (directly or via scoped wording); once trusted leaves cover a record, the deterministic compiler lowers it to canonical DSL. A compiled record publishes only after passing schema, canonical-form, integrity, describer, and cruncher gates and shape approval.

The workbench reads private source prose from `_private/dump.json` and stores its local database under `_private/round5c/`. Run commands from `tools/`:

```bash
cd tools
npm run semantic-authoring -- commands
npm run validate         # schema + referential integrity
npm run audit:coverage   # re-measure coverage
```

Commit only structured DSL diffs under `data/enrichment/<faction>/abilities.json` and community-authored notes. Keep all source prose under gitignored `_private/` (inspect with `cd tools && npm run prose -- get <faction> <ability_id>`).

## Core Data

Core data files (stat lines, point costs, faction/unit/weapon definitions) live under `data/core/`. Fabricated examples demonstrating the schema shape live in `data/core/_example/`.

### Base Sizes

Unit and per-model `base_size_mm` values come from `_private/dump.json` via the `base-sizes` MFM ingest pass. Labelled per-model entries (such as `Sword Brother: 40mm`) are matched to composition models by name; authored oval dimensions within 1 mm of the dump value are preserved. Unmeasured categories (`Hull`, `Large Flying Base`, `Unique`) and unmatched labels are reported rather than guessed.

```bash
cd tools
npx tsx src/ingest-mfm.ts base-sizes           # dry run (report only)
npx tsx src/ingest-mfm.ts base-sizes --write   # patch data/core/*/{units,unit-compositions}.json
```

Reports are written to `data/core/_reports/mfm-base-sizes.md`, and unattributed rows to `_private/mfm/unmatched-base-sizes.json`.

Entries without dump dimensions (`flying-base`, `hull`, `unique`) keep `"draft": true` until real dimensions are filled in manually. List remaining draft entries with:

```bash
jq -r '.[] | select(.base_size_mm.draft) | .id' data/core/*/units.json
```

After editing schemas or data, run `just regen` from the repository root to regenerate TypeScript, Rust, Python, Go, and conformance artifacts in order. Any conformance change bumps `conformance/SPEC_VERSION`; package releases update all four version files (`tools/package.json`, `crates/wh40kdc/Cargo.toml`, `python/src/wh40kdc/_version.py`, `go/version.go`) together.

## Tooling and Pre-Push Verification

1. Fork the repository and create a feature branch.
2. Make your changes and add tests.
3. Run `just preflight` from the repository root to execute the full data, library, formatting, and parity check suite used by CI. For quick inner-loop iteration in TypeScript, use `cd tools && npm test && npm run validate`.
4. Open a PR.

## Cross-Language Parity

TypeScript, Rust, Python, and Go (with R planned) are held in parity by the shared corpus in `conformance/` (see [`CONFORMANCE.md`](CONFORMANCE.md) and [`conformance/RUNNER_PROTOCOL.md`](conformance/RUNNER_PROTOCOL.md)).

**Second-implementation rule:** Any new or modified golden in `conformance/` must be independently reproduced by at least one other implementation in the same PR. The same contributor may implement and verify both sides.

### Workflow for Behavioral Changes

1. Implement the change in one language.
2. Regenerate or update the affected goldens (`cd tools && npm run gen:conformance` for TypeScript).
3. Update and verify at least one other implementation (`cargo test -p wh40kdc`, `cd python && pytest`, or `cd go && go test ./...`) and run the parity differ (`python3 tooling/parity/differ.py --pair ts,<rust|py|go>`).
4. Include the implementation diffs, corpus diff, and verification in the same PR.

Bump `conformance/SPEC_VERSION` (single integer) for any semantic corpus change (added, changed, or removed cases, runner protocol changes, or invariant changes). Pure formatting edits do not bump it.

### Adding a Language Port

1. Implement the public API surface defined in [`CONFORMANCE.md`](CONFORMANCE.md) (Dataset queries, roster import/export, cruncher, abilities resolver, scoring, terrain, describers, validator).
2. Ship a runner binary implementing [`conformance/RUNNER_PROTOCOL.md`](conformance/RUNNER_PROTOCOL.md).
3. Register the runner in `tooling/parity/` so CI can diff it against the existing ports.
4. Pass all native conformance tests and `python3 tooling/parity/differ.py --pair ts,<your-lang>`.
5. Document the port in [`README.md`](README.md) and [`CONFORMANCE.md`](CONFORMANCE.md).

### Python Development

```bash
cd python
uv venv && uv pip install -e ".[dev]"
pytest            # unit + conformance tests (reads ../conformance/)
ruff check .
mypy src
```

Regenerate checked-in Python artifacts after schema or data changes (bundles derive from Rust's `bundle.generated.json` for deterministic file-walk order):

```bash
cd tools && npm run bundle:schemas && cd ..
cargo run -p xtask -- bundle-data
python3 python/codegen/sync_bundle.py
python3 python/codegen/sync_spec.py
python3 python/codegen/gen_typeddicts.py
```

Run Python parity diffs:

```bash
python3 tooling/parity/differ.py --pair ts,py
python3 tooling/parity/differ.py --pair rust,py
```

### Go Development

```bash
cd go
go test ./...     # unit + Go-native conformance tests
go vet ./...
gofmt -l .        # must produce no output
go build -o wh40kdc-runner ./cmd/wh40kdc-runner
```

Regenerate checked-in Go assets after schema or data changes:

```bash
cd tools && npm run bundle:schemas && cd ..
cargo run -p xtask -- bundle-data
bash go/codegen/sync.sh   # updates go/{bundle.json,share_registry.json,schemas/,spec.go}
```

Run Go parity diffs:

```bash
( cd go && go build -o wh40kdc-runner ./cmd/wh40kdc-runner )
python3 tooling/parity/differ.py --pair ts,go
python3 tooling/parity/differ.py --pair rust,go
python3 tooling/parity/differ.py --pair py,go
```

## Conventions

- JSON files: 2-space indentation.
- Entity IDs: kebab-case (`space-marines`, not `SpaceMarines`).
- Data files: JSON arrays with one entity per element.
- Commit messages: conventional commits (`feat:`, `fix:`, `chore:`, `docs:`, `test:`).
